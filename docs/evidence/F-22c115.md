# F-22c115 — In build mode the stranding rule reads where the builder stands

Date: 2026-11-22

A CI census child, at the lead's word. **Build mode only:** the modes that run `BuildRunner` without `PortalRunCampaign.plan()`:
- Builder;
- a base built with no goal;

Goal mode is unchanged: `plan()` sets the same two fields, as before.

## Scope and implementation

**Found:** `NativeBaseGameTests`' stone-tools cabin failed on CI twice, both with the same signature: "kept out by {on its site=6, stranded=12} … stranded from 0, 0, 0 after 3 refused walks".

| Run | Where |
| --- | --- |
| 45009921929, attempt 1 | #451 |
| 44908125381, attempt 2 | an earlier PR's re-run |

In #451's log the builder then looped 149 times between two steps:
- "Explore south for logs" (`BuildRunner`:937);
- "Back up to the build" (`BuildRunner`:910).

**Cause:**
1. `PortalRunCampaign`'s stranding rule counts refused walks from where the player stood, as `lastFeet` and `lastTick` record it. A walk from somewhere new lapses the count.
2. Only `plan()` set those two fields, and in build mode `plan()` never runs. So `lastFeet` stayed at the origin (0, 0, 0) and `lastTick` went stale.
3. After three refused "Walk to stone" walks the builder was stranded, and it stayed stranded however far it then walked. Stranded, its gather offered no walk to a tree.

This is not F-22c73's case. That one was refused pick-up walks in its pit, which no longer count. Its row now says so.

**The change (`PortalRunCampaign`):**
- A new `standing(body)` records the body's feet and the server's tick, as `plan()` does.
- The build's entry points call it first:
  - the gather (and `stoneFor` through it);
  - `knownLogsKeptOut`;
  - `lookFor`;
  - `climbOut`;
  - `buildRoute`, which every overload ends in;
  - `tunnelAlong`.
- In goal mode these run on the tick `plan()` already ran, so the values are the same.

Nothing is granted, and no check, bound or timeout is loosened.

Changed files:
- `PortalRunCampaign`;
- `NativeStrandedPickupGameTests` (two tests).
