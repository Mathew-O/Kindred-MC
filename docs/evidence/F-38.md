## Scope and implementation

User-visible behavior: none intended on vanilla. Core now asks what a thing is instead of comparing names, so the
later slices can hand it a server's own tags (a mod's tagged log is a log).

Changed modules/files (slice 1, companion-core only):
- `VanillaIds` (new): the one main class in core that names `minecraft:` ids. Groups stand for a tag (exact when
  the list is that tag's vanilla 1.21.1 content, so the server's tag replaces it; not exact when no tag says the
  same, named in the `kindred` namespace); single ids each say the tag, component or attribute they would use;
  vanilla tool tiers.
- `Capabilities` (new): an immutable snapshot of plain strings (group members, tool kind and tier). Vanilla from
  `VanillaIds` until the adapter installs the server's (slice 2); `install` and `reset` swap whole snapshots.
- `InventorySummary`: `count(Group)`, `has(Group, n)`, `hasTool(kind, tier[, maxTier])`.
- Migrated by meaning: `logistics/ChestOrganizationPolicy` (categories by group), `progression/` (logs by
  `#minecraft:logs`, planks by `#minecraft:planks`, pickaxe, sword and hoe checks by tool kind and tier),
  `idle/IdleObservationController` (trinkets: `#minecraft:saplings` plus a kindred group).
- Moved to `VanillaIds` constants, behaviour unchanged: every other `minecraft:` literal in core's main sources,
  except those below.
- `VanillaIdsLiteralTest` (new) with `f38-literal-baseline.txt`: a file may not gain a literal, an unlisted file may
  hold none, and a file that lost some must have its line lowered.

Not touched, by claim (Active work): `factions/SafeZones` (2), `factions/Territory` (2), `market/MarketTable` (1);
they stay in the baseline until FACTIONS A's claims end. Also not touched: `record/`, `rescue/`, `wire/`,
`chronicle/`, `knowledge/`, `match/MatchRegistry`, NativeNavigator and movement (none held literals).

Dependencies satisfied: none needed.
Schema/configuration changes and migration coverage: none. No saved key, NBT or SQL field changed.

## Remaining limitations and handoff

Slice 2 (adapter, `claude/refactor-tags-1109-2`): `KindredCapabilities` builds the snapshot from the server's
item tags (block tags where no item tag exists) and each tool item's class and material, on the server thread at
`SERVER_STARTED` and after each successful datapack reload, and clears it at stop. The progression craft's plank
fallback tries vanilla's woods in the old order, then any other `#minecraft:planks` member by id (on vanilla that
adds crimson and warped planks, the widening noted above).

Slice 3 (`claude/refactor-tags-1109-3`), palettes by the wood held:
- core: `Capabilities.Wood` (a wood's family by full id; vanilla's eight from `VanillaIds` as always named, the
  server's others after; planks builds never used, the Nether stems and bamboo, kept out), `construction/Woods`
  (a build's parts by its wood's family; an unknown name falls back to the vanilla naming, as saves had it);
  `BuildNeeds.recipe` and `gathered`, `BuildStyle` (a wood is any `Woods.known`; `woodOf` adds the server's woods),
  and the generators (`Houses`, `Compounds`, `Bunkers`, `TradingHall`, `Generators`, `BuildBattle`) by `Woods`.
- adapter: `KindredCapabilities` reads each `#minecraft:planks` item's log from its crafting recipe and its stairs,
  slab, fence, gate, door and trapdoor by the wooden tags, and keeps the recipe that makes each server wood's planks
  (an id like `minecraft:bamboo_mosaic` can name another recipe); the base and hall checks use `Woods.known`; the
  wood at hand and the ranch's wood also read the server's woods by tag.
- Seen while writing the fixture: once the player has crafted a table and cannot place it, its loop asks
  `native_place` about 32 times a second ("Block placement produced no effect or was obstructed") until something
  else wins; not F-38's, left for the owners of placement.

Slice 3, needs and worth:
- `guide/Need` is a record read from `guide/needs.txt` (the vanilla needs resource: name, word, plural, cap, what
  satisfies it, how it is got), in the old order; the fifteen constants, `name`, `ordinal`, `values`, `valueOf` and
  `parse` keep the enum's meaning (`NeedRecordTest`). EnumMaps in `NeedsAssessment` and `MinecraftGuide` are maps in
  the needs' order; the adapter's `FollowUps` switches on a need's name (a need the vanilla set lacks has no
  follow-up); the OpenAI schema lists the names; Claude's structured follow-up takes the name as a string, which
  `Want.parse` already filters (an enum there would be a second list of needs).
- `Worth`: vanilla's table stands for vanilla's items; another namespace's item it does not name is worth its
  cheapest recipe's inputs over its yield, through the tree (four deep, no cycles), by the recipes the adapter reads
  into `Capabilities` (crafting and smelting, outputs outside vanilla's namespace) (`WorthDerivedTest`). Found on the
  way: `Worth.kit` cut vanilla's prefix length off any id, so a mod's short id (`mymod:odd`) threw; it takes the path.
