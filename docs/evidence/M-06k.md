# M-06k evidence: the month run's load

M-06k is the month run on the owner's server (the tracker's row). Its hitches are attributed by cause below
(2026-11-12); this file holds what has been measured, one slice at a time.

## The gather's best-tool question asked once per kind of block (2026-11-11, claude/m06k-gather-tool-cache-1111)

After the safe zones' fix (M-06f, #185), a JFR profile of seed 110 Factions (`115c960`, alone, 288,000 ticks) still had
`WorldKnowledge.nearest` at 9.42% of the server thread's samples against 2.85% in a quiet stretch, and under it
`NativeBreakAction.bestTool` at 2.81% against 0.30%. The goal's gather and its walk-out stop
(`PortalRunCampaign.gather`, through `gatherFrom`, and `stopFor`) search every remembered block of a kind with one predicate,
`gatherable`, and that predicate asked `bestTool` (a pass over the 36 inventory slots) for every block that passed its
cheap filters. The answer depends on the block state and the inventory alone, and a search does not change the
inventory.

Change, no decision changed: `gatherable` keeps a map from block state to the answer, made with the predicate, so it
lives for one gather's or one stop's search within a tick and is never kept across ticks. `mayWork` (the world's rule
and the territory guard) now runs before it. The two checks are pure predicates, with no side effects and no counters
(`mayWork` is `canPlayerModifyAt` and `TerritoryGuard.mayChange`; the tool check reads the inventory), so changing
their order cannot change any answer.

**The same answer, pinned first.** `NativeGatherTargetGameTests` (GameTest, a bare native body and one campaign): rock
in cobblestone, deepslate and stone (with the block it stands on remembered, never its own support), iron and diamond
each in deepslate and stone, and three logs of which only one is a tree's (one a post against planks, one held up by
leaves). The cell gathered first is asserted for rock, iron, diamond and logs across seven inventories: a bare hand, a
wooden pickaxe off the hotbar, a golden, a stone and an iron pickaxe, a stone pickaxe with the caller's rule excluding
the nearest rock and iron, and a bare hand again on the same campaign (nothing found with a pickaxe kept for a hand).

## The hitches attributed by cause (2026-11-12, claude/m06k-hitches-1112)

No code changes. Measured on main at `783c9159`, with the server jar built from it and the run alone on the cores. The scenario is the 8-player Factions run on seed 101: starters Kindred, Sol and Echo; players Ada, Bram, Cleo, Dara and Eli; 3 founders; goal none; `maxNativePlayers=8`, `bases=true`; 72,000 ticks with sprint on. That is keepdb8's scenario (the [operator guide](../operator-guide.md)), which ran a mean of 32.3 ms a tick with no profiler.

**Method.**
- **Profiler.** The pack's own spark mod (1.10.109) ran beside Kindred, driven by two commands over the server's RCON. The RCON was on a random local port with a fresh random password per run, and neither was recorded.
  - `spark tickmonitor --threshold-tick T` logs each tick over T ms. It also logs each GC, together with the tick it fell in.
  - `spark profiler start --only-ticks-over T --timeout 1800 --save-to-file` samples the server thread every 4 ms with spark's built-in Java sampler. It keeps only the samples from ticks over T ms.
  - Each band was its own run: T = 200 ms, then T = 50 ms.
- **No upload.** The profile was written to the server's own `config/spark/` folder; the log reads "Data has been written to: ./config/spark/profile-….sparkprofile". No profile URL was printed and no viewer was opened. No command used spark's upload or its viewer. (spark's timeout path prints its fixed "Uploading results..." line before it saves; with `--save-to-file` it saves to disk instead of uploading.) The server ran in offline mode with query off.
- **Decoding.** The saved profile was decoded locally with spark's own protobuf classes. The server thread's call tree was flattened, and each node's own time (its time less its children's) was counted. Frames were mapped from intermediary names to Yarn names using the pinned Yarn mappings (1.21.1+build.3).
- **Causes.** Each stack was put under the first cause it matches, checked in this order:
  1. chunk generation or IO: `ServerChunkManager.getChunk`, the chunk loading manager, world gen, storage, region files;
  2. the navigator's searches: `NativeNavigator`, `NativeRoutePlanner`, `MovementSkills`;
  3. knowledge and atlas sweeps: `WorldKnowledge`, the atlas, `AtlasRecall`, `KnowledgeWebs`;
  4. the metadata writer's handoffs: persistence, `PlayerRuntime.handBack`;
  5. Kindred's other decisions: the rest of `dev.kindred`;
  6. entity ticking;
  7. world ticking;
  8. network;
  9. autosave;
  10. other.
- **GC.** GC pauses are not sampled. A band's GC share is therefore the tick monitor's GC time inside that band's ticks, divided by those ticks' total length. The profile's own split covers the rest.
- **Tools.** The tooling stayed out of the repository: a copy of `tools/eval/run.py` that adds the spark jar and RCON, the RCON driver, the decoder and the classifier.

**What this says.**
- **Ticks over 50 ms.** These are mostly the navigator's searches: two thirds of the band's time. The single largest leaf is the fluid check, `Navigator.swimmable`, made for each move the search tries.
- **Ticks over 200 ms.** Here the navigator is about half, and chunk generation or IO is a third. 21 of the 24 fell in the first 13,600 ticks, which fits players walking into new chunks; that reading is not measured.
- **What is not the cause.** GC pauses, the metadata writer and autosave are not the hitches.

This attributes the hitches and claims no fix.

**Limits.**
- **Worst ticks' paths.** spark adds all the qualifying ticks of a band together and keeps no per-tick stacks. So "the top 3 call paths of the worst ticks" are the band's top paths, and the worst ticks themselves are named from the tick monitor, not split by cause one by one. In the 200 ms band, the 24 ticks share one profile.
- **The sampler.** The built-in Java sampler sees only Java frames, at safepoints, every 4 ms; it is not the async profiler. A 200 ms band of 24 ticks is about 1,750 samples.
- **The bands overlap.** The 50 ms band includes the ticks over 200 ms.
- **Cause order.** The cause order decides mixed stacks. A navigator search that loads a chunk counts as chunk work, because chunk work comes first.
- **One run each.** Each band is one run of one seed, with the profile's window the run's first 30 minutes (35,434 and 42,467 ticks of about 72,400). No other seed was measured.
- **spark's own cost.** spark raised the eval's mean tick to 38.07 ms and 34.66 ms, against keepdb8's 32.3 ms without it. spark also loaded its ByteBuddy agent locally, and the log carries its Java-agent warning.

**A first method, discarded.** An earlier attempt with JFR (execution samples, plus the server thread's parks recorded at threshold 0 to find each tick's edges) was dropped, and its numbers are not reported. There were two reasons:
1. **Merged ticks.** When the server was behind, its back-to-back ticks had no park between them and merged into one. The recording found 21,933 "ticks" for 36,000 run.
2. **Recording overhead.** The recording's own cost raised the eval's mean tick to 46.8 ms, against keepdb8's 32.3 ms. A tick that long is no longer the run being measured.

## Remaining limitations and handoff

The hitches are attributed (2026-11-12, above). Most of the time in ticks over 50 ms goes to the navigator's searches under `nearestReachableDryStand`. Ticks over 200 ms add chunk generation or IO as a second cause. Any fix is held until the owner decides on the performance campaign. Two other items stay outside this slice:
- **The gather.** The gather is chosen again and again where every known log was refused by the territory guard (seed 110's recapture). That is M-06i's, and its plan sets it aside on claude/m06i-refused-logs-1111.
- **The month run.** The month run itself is not run.
