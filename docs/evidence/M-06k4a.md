# M-06k4a — A stop that hangs at "Saving worlds": its threads dumped, and a save that cannot be lost

Date: 2026-11-21
Agent / branch: Claude Session A (`claude/m06k4a-stop-watch-1121`, off main `b2219f3f`)
Status: in review (harness and docs only; done once CI is green on its PR). The hang's cause is not found: this files the means to find it and a mitigation for the month run.

## The hang

Twice an evaluation run's own stop logged "Saving worlds" and never saved:
- **M-06k4's walk** (main, 2026-11-14): 20 minutes, "the server thread in `ServerChunkLoadingManager`'s save loop, with no Kindred frame on any busy thread"; killed; the next start loaded normally. Its three thread dumps were kept with the walk, not committed.
- **M-06i2c5's comparison** (seed 109, bases off, 2026-11-21): its result written at 08:34:59; the console's last lines "Stopping server", "Saving players", "Saving worlds", then Kindred's own "memory files written at the stop in 24 ms" on its own thread; no "Saving chunks for level" after it. It stood there until `run.py`'s `--timeout` killed it (7,325 s). Its world was removed by `run.py`, so what it held could not be read.
- **Its replicate** (the same jar and arm, alone, `--keep-world`, a thread-dump watcher armed): saved and exited, "Saving worlds" 14:47:30 to "All dimensions are saved" 14:47:31. Across the 73 evaluation runs kept from M-06i2's comparisons, one hung.

**Where vanilla 1.21.1 waits** (the yarn-mapped jar's bytecode). After "Saving worlds", `MinecraftServer.shutdown` loops while any world's `ServerChunkLoadingManager.shouldDelayShutdown()` (lighting updates, chunks to unload, chunk holders, unsaved points of interest, unload tasks, the chunk task queue): each pass removes the persistent tickets (all but `UNKNOWN` and `POST_TELEPORT`) and ticks the chunk manager, then runs the server's queued tasks; only then `save()` logs "Saving chunks for level". So a chunk that never unloaded held it. Kindred's one hook in that span (`ServerSaveTimeMixin`) notes two times; its own chunk tickets are of the kind the loop removes. Not ruled out: a player still in a world, or a task that keeps a chunk loading on each pass. The evaluation run stops with `server.stop(false)`, as the console's `stop` does.

## The change (harness and docs only)

- **`tools/eval/run.py`:** where a server's console has stood at "Saving worlds" 120 s (`STALL`) with no "All dimensions are saved", three thread dumps 10 s apart (`jstack -l`, else `jcmd … Thread.print -l`) and the world's file times (`level.dat`, `level.dat_old`, `session.lock`, the region files of each dimension, the companion database) go to the seed's `stall/` folder, which is kept with its log; at 600 s (`STALL_KILL`) the server is killed, its result already written, rather than standing until `--timeout`. A stop that saves is left alone.
- **`docs/operator-guide.md`, Stopping:** before `stop`, `save-all flush` and its "Saved the game"; then a stop that hangs cannot lose what was built since the last autosave. In place until the hang's cause is found.
