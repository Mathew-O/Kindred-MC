## Scope and implementation

User-visible behavior: when a stuck spell gets out by the strategist's plan, the server keeps a recipe: the steps that
ran, as far as each went, and the kind of scene they worked in. The next time any player on the server is stuck a minute
in the same kind of scene, the recipe is tried first with no model call. One that works gains weight. One that fails
twice in a row is dropped. One that fails once hands over to the strategist's first round, which is told what the recipe
did. At most 500 recipes are kept, in `<world>/kindred/rescue-recipes.json`.

Changed modules/files:
- `companion-core`:
  - `rescue.RescueSignature` (new, pure): coarse features of the slice as the player sees it, and of its kit: the walled
    sides within two blocks, the room overhead up to four, what is underfoot, liquid above, below or beside, whether a
    wall it cannot break hems it in, dark, a ledge within a pillar's reach, a shaft one wide, blocks carried, the
    pickaxe's tier in four buckets. No coordinate. `key()` is what two scenes match on.
  - `rescue.RescueRecipes` (new, pure): the book, at most 500, the heaviest match first, `learned`, `worked`, `failed`
    (retired at two in a row), the lightest giving way when full; entries not of the vocabulary are left out as read.
  - `RescueRecipesTest` (5).
- `companion-server-adapter`:
  - `RescueRecipeStore` (new): the server's file, read at start (the mod's starter set when there is none), written
    whole off the server thread whenever the book's revision moves.
  - `PlayerRuntime`: one book for the server, handed to each player's goal with the skills installed; `recipesForFixtures`.
  - `PortalRunCampaign`:
    - `tryRecipe`, when a spell opens.
    - The steps that ran (`ranSteps`), kept when a spell gets out by a model's plan, once that plan has ended (`learn`).
    - A recipe's failure counted when its plan stops or its twenty seconds pass with no progress; its success, by weight.
    - The lines `rescue recipe: spell N, <steps> (weight W)`, `rescue recipe kept: <steps> (weight W)` and
      `rescue spell N: out|not out by its recipe`.
- gametest:
  - `NativeRescueRecipesGameTests` (new, 2), and its entrypoint.
  - `NativeRescueGameTests`' helper reads only the plans' lines, now that spell and recipe lines follow them.
- `tools/eval`:
  - `score.py` and `compare.py`: recipes tried first, and spells out by a recipe.
  - `run.py`: each run keeps its server's recipe file beside its result; `--recipes` starts each world with one.
  - `seeds-20.txt` (new, for F-29e): the ten seeds, and ten rolled for it, none of them E-40's reserved gate seeds.
- No new dependency (the file is written with Minecraft's own Gson, as the player memory is); the manifest is unchanged.

Schema/configuration changes: `<world>/kindred/rescue-recipes.json` (new): a list of `{signature, steps, weight,
failures, source}`. It is read once at start and an unreadable file is left aside: the starter set is used and the log
says so. Nothing is migrated. A world without the file behaves as before until a spell gets out by a plan.

## What the design said, checked against the code

| Claim | Found |
| --- | --- |
| "the scene is also captured as a replay (F-27) at the spell's start" | It is captured when a model's plan arrives, before it runs (F-29's capture, kind `stuck`), which is the spell's start give or take a round. A recipe's own run captures nothing new |
| "the hardest block hemming it in and whether its tool breaks it" | Kept as one feature: whether any block hemming it in is one it cannot break. A finer "hardest block" would split scenes that a recipe treats the same |
| "Two scenes match when their features agree" | As built: exact equality of the key. The kit's two features (blocks carried, pickaxe tier) are part of it: a pillar recipe is of no use to a player with no blocks |
| "kept per server ... shared by every player" | One book in the runtime, handed to every player's goal |
