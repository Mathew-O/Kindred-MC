# F-26a — Work handed back to the server thread runs within a tick on a sprinting or overloaded server

Date: 2026-11-04
Agent / branch: Claude / claude/e40-ladder-1104 (E-40's ladder, rung a)
Build: on top of `f0258b6`; recorded in [validation](../validation.md)
Status: complete (native). Its effect on the ten seeds is in E-40's next evaluation.

## Scope and implementation

User-visible behavior: on a server that sprints through its ticks (`/tick sprint`, as the evaluation engine F-26 runs
every seed), or one too loaded to keep up, the AI players work at the pace they keep on a server at 20 ticks a second.
Before, every task they did took about twice the game time there, and the evaluation measured them at that pace.

Found: chasing the most common stuck cause on the ten seeds of main (`f25c4ax-84b331c`, E-40's starting build): 45 of
144 recorded stuck spells were branch mines for iron at Y=16 to 21.
- **Echo, 8675309, at 40, 19, 67:** its tunnel's legs were 20 blocks long and 3 apart. Its first spell came on the third
  leg of one 8-block cell column, after two legs over cells the first had shown.
- **The same mine, one player, off a sprint:** 42 ticks a step (160 blocks in 6,797 ticks). The watchdog does not fire:
  the longest stretch without a new cell is about 2,000 ticks, against its 3,600.
- **In the evaluation:** about 100 ticks a step. A task-by-task count on 8675309 (a diagnostic build, not kept) showed
  why. Each task waited 5 ticks after the last had ended, then 9 from being asked for to starting. A stone break ran
  27 ticks, 12 of them breaking.
- **Not the thinking budget.** The evaluation's new ten-minute report gives each player's goal its slice every 5 ticks:
  7,200 slices in 12,000 ticks for three players, 170 µs a slice, about 20 refused for time.
- **The cause is vanilla's queue.** A task queued from another thread runs only once it is more than three ticks old
  when the server is sprinting, or behind and with no time left in its tick (`MinecraftServer.canExecute`). Each of a
  task's hand-backs cost four ticks:
  - the activity budget read, then its save, before it starts;
  - the action record written before a break, then closed after;
  - the last task's activity closed before the next is asked for.
  At 20 ticks a second with time to spare, the same hand-back runs within the tick.

Changed modules/files:

- `companion-server-adapter`:
  - `PlayerRuntime`: its hand-backs to the server thread (`server.execute`, 105 places) go through `handBack`. A task
    is still given to the server's own queue as before, and also to the runtime's queue. `runHandedBack` runs that
    queue as each server tick starts, in the order the tasks came. A task runs once, whichever way comes first, and
    one that fails is logged as the server's queue logs it.
  - On the server thread, or once the server has stopped, a task runs at once, as `server.execute` does.
  - Runtimes are kept in a weak set, so a fixture's runtime is not held after its test.
  - `KindredMod`: the start-of-tick hook runs `PlayerRuntime.runHandedBack` before the runtime's tick.
  - `EvalBootstrap`: every ten game minutes the console gets the thinking slices by kind, the slices refused for time,
    and their time.
- gametest: `NativeBranchMineGameTests.onASprintingServerABranchMineThroughFreshStoneKeepsItsPaceAndIsNoStuckSpell`
  (new, registered after `NativeAtlasGameTests`).

## Remaining limitations and handoff

- The waits for the store's writer are still real time. A hand-back now costs at most a tick on a sprinting server,
  plus whatever the write takes.
- Earlier evaluations measured the players at the slower pace. E-40's comparisons say so where they compare across this
  change.
- The other classes that hand work back (`StrategistBridge`, `PeerRadio`, `PlayerVoice`, `KindredPanelService`,
  `KindredSkins`, `TalkSettings`) still use the server's own queue. None of them is on a task's path.
