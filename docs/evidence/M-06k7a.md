## Scope and implementation

Found by M-06i4's rehearsal: after a restart at world time 61,286 the first `Kindred cost:` line read `day 1` again. It
was numbered by this start's server ticks (`server.getTicks() / 24000 + 1`), so every start counted from 1, and the
pre-flight report, which keys growth and the month projection on the day, merged different days from different starts.
The month run restarts the server, so its report would have been wrong from the first restart. The lead: "the cost
line's day fix is your next block. It must be in the jar the owner starts the month run with."

User-visible behaviour: the line now reads `Kindred cost: world day N: …`, where N is the overworld's game time in whole
days, from 1 (`RecordGauge.worldDay`). A restart goes on with the world's count. The period (every 24,000 server ticks
and at each stop) and every other field of the line are unchanged.

Changed files:
- companion-server-adapter: `RecordGauge` (`DAY_TICKS`, `worldDay`, the line's "world day"), `PlayerRuntime`
  (`logCostNow`, used by the periodic line and the stop's line).
- tests: `RecordGaugeWorldDayTest` (new, JUnit), `NativeCostGameTests.afterARestartTheCostLineGoesOnWithTheWorldsDay`
  (new GameTest).
- tools: `soak/preflight.py` (reads both forms), `soak/test_preflight.py` (one new case, one updated),
  `corpus/report.py` (skips both forms), `corpus/test_leftover.py` (the world form).
- docs: `operator-guide.md` (the cost line's description and the pre-flight report's).

How `preflight.py` tells the forms apart: the word `world`. `Kindred cost: world day N:` is the world's day; growth is
keyed by the day alone and read across a stop, and a later line for the same day (the stop's, after the periodic one)
replaces the earlier. `Kindred cost: day N:` (logs from before this fix) counts from its start; a drop in the number
begins a new start, and growth is never read across a start or across the two forms. Each growth entry says which it
counted (`dayCounted`: `world` or `start`).

Schema or configuration changes: none.

## Limits

- No live run: the fix is proven by the JUnit and the native fixture, not by a restarted server's log. The month run's
  first restart shows it live.
- The line is still logged every 24,000 server ticks from the start, not at the world's day boundary, as the lead asked;
  so a start's lines fall at the same world-day offset as its start, and two lines can carry one day (the later
  replaces the earlier in the report).
