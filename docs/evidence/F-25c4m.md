## Scope and implementation

User-visible behavior: none in play. The server log gains two lines, for an operator or developer:
- a player with a goal that has started no skill for a minute of game time says once which of its gates holds it;
- a task accepted for dispatch and dropped before its skill started says which gates dropped it, at most once a minute.

Found in the live runs on `10a60d5` (seed 8675309, strategist off): Kindred collected its smelted iron at 10:21:39, then started nothing for the seven minutes until the run ended. Its goal went on offering steps every few seconds, and its watchdog fired every 50 seconds or so ("no progress here for a while - try elsewhere"). Nothing in the log said why: no refusal, block or cancellation.

Reading the code found four places such a stall would leave no trace:
- the decision gates (`mayDecide`), none of which logs;
- the dispatch's asynchronous continuation. `dispatchNativeTask` returns 1 before it runs, so the goal sees the task accepted. A later drop there (the generation, a stop, a cancellation, a hazard interrupt, an unpaid slice or a refused start) was silent, and a goal that offers the task again each tick would stand still unsaid;
- a chosen task that fails its check that it can still be done (`validateCandidateStillExecutable`). It is dropped and asked for again. A step of higher priority failing it every tick would hide the goal's steps for good. A team hand-over's craft, which ran unlabelled at 10:21:34 just before the stall, is such a step;
- a team task that could not be claimed.

Changed modules/files:
- `PlayerRuntime`:
  - a stall line after each decision: "has started nothing for N ticks on its goal", with `mayDecide`, the admission, the candidates, the decision and `nativeStatusLine`'s gates;
  - `dispatchDropped`: "dropped before it ran", with the gates, from the three silent drops in the dispatch, a failed check that the task can still be done, and an unclaimable team task.
