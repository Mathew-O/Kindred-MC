## The bug it found

`PlayerRuntime.ChronicleHost.players()` counted a player's native body among its actors only while the body was
connected (`nativeBody.connected()`). The Chronicle gives a player's page the events whose actor is one of the
player's actors. So a day's pages written while a body is offline:
- skipped everything the body had done since the last page;
- moved `through` past it, so those events never reached a page.

After a restart the bodies wait offline until connected, so in the month run any day ending in that window lost its
pages.

On main the test fails at the second new day: "Day 2150's two pages: 0, through 17582, idle true". Every event of that
day was read, and none was anyone's.

## The fix

`ChronicleHost.players()` always counts the body's saved id (`entry.data.entityId()`), connected or not. The connected
body's id is still added as before.

Two checks (the lead's):
- **Which id.** `entityId()` is the body's saved player UUID (`java.util.UUID`; `NativeStatus.nativeId` reports the same
  value), not Minecraft's per-session integer entity id. It is the UUID the native body logs in with and writes its
  events under. The weeks fixture shows it: before any restart, events recorded under `nativeId` were paged through
  the connected body's id.
- **No double paging.** The actors are a set, so the saved id and a connected body's id, being the same UUID, are one
  actor, and each event is matched once. The month test asserts that each new day's events are cited at most once in
  each player's pages and that each day's death is on its own day's page. The connected case is
  `aPlayersDayBecomesItsPageAndNoEventIsToldTwice`, which runs with the body connected and asserts that no event is
  cited twice; it passes unchanged.
