## Scope and implementation

User-visible behavior: none yet. The runtime still opens a budget with `openBudget`, and `/aiplayer limit timezone` still rejects. This slice is the rule and the storage the runtime needs before either can change.
- Today an activity request computes the local day containing now and calls `openBudget`. That throws when the day overlaps or precedes the latest saved period. The dispatch path turns the throw into a metadata fault and halts the player pending reconciliation.
- Two ordinary events cause that: the wall clock stepping back over midnight (an NTP correction), or a timezone edit, which is why the timezone command is switched off.

Changed modules/files:
- `companion-scheduler/.../PeriodTransition.java` (new): where activity at an instant is charged.
  - `CURRENT`: the latest saved period still contains the instant. A zone edit waits for its end.
  - `OPEN`: a period to open. That is the first one, or the local day containing the instant once the latest has ended.
  - `CLOCK_BEHIND`: the clock is before the latest period, and an earlier period never reopens. It names when the latest starts.
  - `ZONE_PENDING`: a zone edit waits for its first local day that starts at or after the latest period's end. It names when that day starts.
- `companion-scheduler/.../ScheduleClock.java`: `transition(now, zone, latest)` and `firstPeriodFrom(zone, closedThrough)`. Both are built on the existing `openPeriod` rule, with the latest saved period's end as `closedThrough`.
- `companion-persistence/.../SqliteCompanionStore.java`: `chargeableBudget(companionId, now, zone)` reads the latest period and opens a new one in the same writer transaction. It writes nothing for `CLOCK_BEHIND` or `ZONE_PENDING`. `openBudget` is unchanged in behaviour; both share one insert path with its checks.
- `companion-persistence/.../ChargeableBudget.java` (new): the transition and the budget, present exactly when the transition names a period.

Dependencies satisfied: FND-04 (`ScheduleClock.openPeriod`, `AccountingPeriod`), F-11a/F-11b (`BudgetState`, the ordered budget writer).
Schema/configuration changes and migration coverage: none. Periods are the existing `budget_buckets` rows; the latest row's end is the closed-through boundary.
Requirements covered (F-11 card: safe period transitions, no replenishment on restart):
- No opened period overlaps or precedes the latest saved one, so no stretch of time is charged to two periods.
- A saved period is returned as saved, so neither a restart nor a zone edit resets its charges.
- A clock rollback or a zone edit waits, with the instant it ends, rather than throwing. An unsettled slice left in an ended period still throws `IllegalStateException`, as `openBudget` does: that is an inconsistency, not a transition.
