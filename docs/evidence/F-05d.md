# F-05d — Startup ledger admission barrier, connection fencing and authority preemption
Date: 2026-10-17 EDT; report 2026-10-17.
Antigravity / uncommitted main, no commits. Complete for this child slice; parent F-05 and F-13 remain open.

Startup ledger barrier, connection callback fencing, and authority preemption consolidate the single path from observation to mutation, fail closed on unresolved action rows, fence stale connection callbacks, and guarantee no-effect handling on self-swaps and workstation replacements:

1. **Startup Ledger Barrier and Fail-Closed Startup in `companion-persistence` and `PlayerRuntime`:**
   - Introduced `ActionRef`, `LedgerScan`, and `StartupLedgerSnapshot` records in `companion-persistence`.
   - Implemented `SqliteCompanionStore.readStartupLedger(Set<UUID> expectedLogicalPlayerIds)` to query unfinalized rows (`PREPARED`, `DISPATCHED`, `UNCERTAIN`) in the `actions` table for all expected companions at server startup.
   - `PlayerRuntime.start()` asynchronously awaits `readStartupLedger` and `modes` before setting `ready = true`. If reading fails or the runtime stops during startup, the store closes and runtime stays unready.
   - Companions with unresolved action rows are marked with `LedgerCheckState.BLOCKED`, denying `connectNative`, `nativeLifecycle("connect")`, `nativeLifecycle("resume")`, `dispatchNativeTask`, and `nativeMutationAllowed`.
   - Clear companions receive `LedgerCheckState.KNOWN_LEDGER_CLEAR`. Note: per product boundary, `KNOWN_LEDGER_CLEAR` does not prove crash-consistent native saves. Fresh players created via `createNative` initialize in `KNOWN_LEDGER_CLEAR`.

2. **Connection Callback Fencing (`ConnectionToken`):**
   - Introduced `ConnectionToken(long startupGeneration, UUID logicalId, long entryGeneration, UUID requestId, long expectedNativeRevision)`.
   - In `PlayerRuntime.connectNative`, token is registered in `entry.pendingConnection` before initiating the async player data read.
   - When the async callback fires, `token.equals(entry.pendingConnection)` is verified on the server thread. Stale callbacks after `halt()`, `detachNative()`, `stop()`, or a newer connection are discarded without attaching the player body or transitioning state.

3. **Authority, Preemption and Incarnation Validation (Guides 01 & 02):**
   - **Self-Swap Refusal as No-Effect (`NativeSwapAction`):** Self-swap requests (`sourceSlot == targetSlot` or invalid slot range) take admission without physical mutation, record `admission.noEffect` (`ActionRecord.State.FAILED`), and return a blocked step.
   - **Workstation Incarnation Check (`NativeSmeltAction`):** Records `furnaceInstance` at plan time. Validates `currentBlockEntity == furnaceInstance` and furnace block tag at mutation, preventing late writes if the furnace block was replaced with an identical block.
   - **Preemption Guards:** In `PlayerRuntime.dispatchNativeTask`, verifies `!entry.arbiter.cancellationPending() && !entry.hazardInterrupted` before task dispatch.
