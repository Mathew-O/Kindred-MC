## Scope and implementation

User-visible behavior: a native skill that takes longer than five seconds now finishes at real time. That covers a walk of more than about twenty blocks, obsidian with a diamond pickaxe (9.4 s) and stone by hand (7.5 s). Before, each skill ran under one prepaid slice of at most five wall-clock seconds, and a running skill whose slice lapsed was halted ("Stopped or unavailable"), so the goal started it again from nothing.
- This never showed while the live runs sprinted ticks, since five wall-clock seconds held hundreds of ticks. Nor did it show in fixtures: the test server does not wait out its ticks.
- Live run 66, the first long run at 20 ticks a second, had 85 skills halted this way. Nearly all were walks out to look for animals, each cut short after five seconds; the search turned to a new heading every time and never got far.

Changed modules/files:
- `companion-scheduler/.../PaidActivitySession.java`: `renew(hardDeadline)`, `renewing()` and `remaining()`.
  - One durable write settles the active reservation up to the request and reserves the next, with the existing `BudgetState.renew`.
  - The active permit governs until that write is acknowledged on the owner thread.
  - The next permit counts from the request, so the write's latency is charged and comes off the end of the new slice; neither slice is ever extended.
  - A stop, or the old permit lapsing, while the write is pending settles the new reservation for the time up to then, once the write is acknowledged and in order. A backwards sample keeps the whole prepayment.
  - Close while renewing settles the new reservation without owner ticks.
  - A failed or mismatched write blocks and revokes, as any write does.
  - It completes false without a write when there is nothing to renew or no allowance or eligible time is left; the active permit then lapses as before. The session still never renews itself.
- `ActivityPermit.remainingAt(nanos)`.
- `PlayerRuntime` (native busy path): renews the running skill's slice when less than 1.5 s of it is left. Only while the skill is running and paid and still admitted: not stopped, no metadata fault or reconciliation, ledger clear, no pending cancellation or hazard interrupt, body connected. The deadline is the accounting period's end, as for the first slice.

Dependencies satisfied: F-11b, F-04a.
Schema/configuration changes and migration coverage: none. Budgets keep the same saved shape; a renewal is one ordinary budget write.
Requirements covered: the activity rules of F-11a/F-11b hold for every slice. No permit before a matching durable acknowledgement. Measurement is rounded up and never extended. Unknown write outcomes block without refunds or retries. Caps and windows are unchanged: renewal grants at most what the cap and window have left.
