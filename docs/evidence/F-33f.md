# F-33f — A day of more than 10,000 events, read whole for its pages

Date: 2026-11-16
Agent / branch: Claude, Session B (claude/chronicle-day-backlog-1116)
Build: the branch's head (see the PR)
Status: complete (the Chronicle's storage path; no body behaviour)

## The finding

Found while checking every limited read of the World Record for F-33e's pattern (the lead, 2026-11-16).

`ChronicleKeeper.writeDay` read a day's events with `host.events(Chronicle.DAY_KINDS, through, BATCH)`. `BATCH` is
10,000, and `DAY_KINDS` includes `journal`. On a day of more than 10,000 such events:
- only the first 10,000 reached the day's pages;
- the rest were carried to the next day's pages, so nothing was lost, but the Chronicle fell further behind each day;
- each page then told of older and older days.

The keyed runs already pass the limit at 3 players. Their journal counts on game day 2 (from their cost lines) were
11,100 in f34c2-37adcdc and 17,295 in f34c3-37adcdc. At 8 players that is roughly 25,000 to 45,000 a game day, so the
month run's Chronicle would have lagged by tens of thousands of events a day.

## The fix

- **`writeDay` reads the whole day.** It reads every batch since the last page (`readDay`), each after the last id
  read, until one comes back short. Each player's events are sorted out as their batch comes, then the pages are
  written once (`writePages`), and the next page starts after the last event read.
- **Off the server thread.** Each batch is read on the Record's ordered writer, as before. Only sorting a batch's
  events by player runs on the server thread.
- **A failed read.** If any batch cannot be read, no page is written and `through` stays where it was, so the next day
  reads the same events again. Nothing is written twice.
