## Event kinds as a registry (2026-11-10)

`dev.kindred.core.record.EventKinds`: a kind is a string registered once by one owner (`core` for Kindred's own); the
same owner again is a no-op, another owner is refused. Core's kinds are registered by value in its static list; their
constants stay in the classes that fold or write them and stay compile-time constants (switches over kinds unchanged).
The adapter's market kinds (`market.intent`, `.cancel`, `.received`, `.uncertain`) are registered by `MarketDesk` as
`kindred-server`, the way an integration registers its own. `SqliteCompanionStore.record` writes only registered kinds:
a batch with another is refused whole as a failed future (logged by the runtime, never thrown on the tick). Saved events
of a kind no longer registered are still read and folded as before. The kind literals left in code became constants
(`Ledgers.CHECK`, `ActionLedgerView.JOURNAL`, `Capture.VULNERABLE`/`SECURE`, `MarketDesk.UNCERTAIN`). No schema change.

The check rebuilds the action ledger from the Record's action events (`ActionLedgerView`). `Ledger.replay` applies

dropped or reordered, and a stop with writes still outstanding still logs the ERROR and reconciles at the next start.

## F-31e: the memory files' last writes at a stop (2026-11-12)

Found while keeping a player's villagers across a restart (F-30d3): `PlayerMemoryStore.close()` only called
`shutdown()` on its writing thread, a daemon, and the chain `finishShutdown` waits for (every player's writes, the
World Record's last write, the store's close) did not include it. What the stop writes to the memory files (each
player's atlas, its peers, its rapport, its stores) could therefore be lost when the process ended at once, or read by
a runtime started again in the same process before it was made.

The fix: `PlayerMemoryStore.closeAsync()` is done once every write already asked for is made (its one thread takes
them in order; a last task after them completes it), and the stop's chain waits for it after the Record's last write,
under the same 10-second bound. `close()` keeps its meaning (it closes without waiting). The stop logs
`Kindred memory files written at the stop in N ms`. No timeout changes; nothing is dropped or reordered; a stop that
times out still logs the ERROR and reconciles at the next start.

## F-31h: the files beside a world, durable across a power loss (2026-11-14)

Claude, Session B (claude/f31h-durable-memory-1114). Ranked first by the lead's test for the month run: thirty days with
restarts loses most if a store's file is lost or corrupted.

**What was there.** Every store of the files beside a world already wrote a temporary file and moved it over the old
one atomically:
- each AI player's memory, bases, work, atlas, peers, rapport, stores and villagers (`PlayerMemoryStore.writeNow`);
- the server's customs (`ServerCustomsKeeper`);
- the model context (`ModelContextStore`).

The readers read only the real file, so **a kill mid-write was already safe**: the old file stays whole. F-31g's kill
soak showed the same. Nothing forced the data to disk before the move, though. After a **power loss or a host crash**,
the move can be on disk ahead of the data, and the file comes back empty or partial. Then:
- the bases, atlas, peers, rapport, memory, customs and model-context readers logged "could not be read; starting
  afresh", and the work reader "none taken up";
- the next write replaced the damaged file, so a player's bases (say) were gone for good;
- an empty file read as nothing at all (Gson's `null`), with no warning;
- only the stores and villagers were set aside.

**The change** (`DurableFiles`, new):
- **A write:** the temporary file is forced to disk, moved atomically where the file system allows, and the folder is
  forced after it, so the move is on disk too. Windows cannot open a folder as a channel; NTFS journals the rename itself.
- **A read:** a file that fails, reads empty, or reads as nothing is moved aside to `<name>.corrupt-<UTC date and time>`
  before anything else is written (another beside it gets `-2`). It is kept on disk and never deleted. The one warning
  says so plainly: "The bases of Rue could not be read; it starts with none of it, and the file is kept: … set aside as
  ….corrupt-20261114-…". The player starts with none of that store, as before, but never silently: an empty file now
  says so too.
- **The stores and villagers** keep their own setting aside, as `<name>.unreadable`, as `StoreMemoryFileTest` has always
  checked. Their reads use the same parse without its move.
- **Off the tick:** every write and read runs on the store's own IO thread, never the server's, so the forces never hold
  up a tick. That covers `PlayerMemoryStore`'s `io` executor (`write`, `save*`, `load*`), `ServerCustomsKeeper`'s
  `io.execute` and `ModelContextStore`'s `io`. The one exception is `ServerCustomsKeeper.open`, which reads its one file at
  start, before the server ticks, as it did.
- **`PlayerMemoryStore`'s warnings** go to its own logger: the same "Kindred" logger, with the same output, so plain JUnit
  can reach them.

Formats, file names and saved keys are unchanged. Persistence only: no body behaviour changes, so no corpus gate.

## F-31f: the agreement check off the writer (2026-11-12)

After F-31d the action ledger's check was linear, but it still ran on the store's one writer, over the whole ledger,
once a game day. Measured on #257's code (a scratch test, not committed): about 17 ms per thousand actions with their
three events each, about 8 ms per thousand folded. At 8 players (keepdb8: about 1,400 actions a game day; 72 game days
a real day) that is about 0.85 s at day 1, 5.9 s at day 7 and 25 s at day 30, every write waiting behind it; the
writer's queue of 256 jobs fills after about 3.6 s at about 71 jobs a second (e40's 191,000 jobs over 144,000 ticks for
3 players, scaled), so from about day 4 or 5 writes would have been refused during each check; and the check held
every row and every action event in memory, about 3 million each at day 30.

**The change.** `SqliteCompanionStore.checkActionLedgerFromSnapshot()` reads on a thread of its own
(`kindred-metadata-check`, a daemon) from a connection of its own, opened by the same driver read-only (its read-only
open flag) with `PRAGMA query_only = ON`; it never writes, and the ordered writer stays the only writer. Both reads, the
table and the events, are inside one read transaction, so they come from one snapshot of the write-ahead log. That is
the same point of comparison as the writer-held check had: every write of the store commits a row and its event in one
transaction, so a snapshot sees the database as it stood between two of the writer's transactions, as the check did
when it ran as one of the writer's jobs. The comparison is streamed: `action_ledger` in `action_id` order, merged with
the `action` and `action.folded` events, each in V13's `(kind, subject, id)` index order and merged by `(subject, id)`;
each action's row from the Record is its last event that reads, as `ActionLedgerView` reads it (an event that is no id,
or has no revision, changes nothing). A row or an event naming an action other than as the store writes its id
(upper case, say) is not read another way and not checked: it is counted, the first 20 kept, and the check does not
agree (`not checked` in the `ledger_check` event, an ERROR naming them), never a pass and never a load of the whole
ledger. The store writes no such id: every row's `action_id` and every action event's subject is `actionId().toString()`
(`prepareAction`, `transitionAction`, `actionEvent`), and the 591 stores on this machine (every fixture world's,
79,617 ledger rows and 238,662 action events; the keepdb8 and factions evaluation stores are no longer here) hold 0. A
disagreement reports how many actions differ and the first 20 (not the whole ledger twice).

At a stop, `PlayerRuntime.stop` calls `stopChecks()` first: the statements under way are interrupted
(`Statement.cancel`), its connection closes, and no check starts after. A check cut short completes with a
`CancellationException`: the runtime logs that nothing was reported, records no `ledger_check` event and runs no fold.
`closeAsync` stops checks too. The writer gains one pragma, additive and reversible (it sets only how far the log is cut
back after a checkpoint; leaving it out restores today's behaviour, and it changes no file's format):
`journal_size_limit` of 4 MB (#227's bound), since a checkpoint cannot pass the check's snapshot while it reads; once
one is past it, the log is cut back. No timeout, no
table, no saved key and no index changes; no write is dropped or reordered; reconciliation is unchanged. The writer-held
`checkActionLedger` stays, as the reference the tests compare against.
