# Kindred MC — autonomous AI players

Build three persistent AI players that earn a cooperative survival playthrough from empty inventory through the Ender Dragon. They have their own goals, needs and team commitments. Humans may cooperate or administer the world. Follow/help/wait are tasks, not the agent's identity.

Read [the player contract](minecraft_player_spec.md), [architecture](docs/player-architecture.md), [canonical tracker](docs/feature-spec.md), [validation](docs/validation.md) and [manifest](release-manifest.json). Current user instructions prevail. The companion product is retired: do not reconstruct its roadmap from old evidence, class names, SQL fields or command aliases.

## Work protocol
- Inspect source and working tree; preserve unrelated work. Claim an open feature ID and intended files in Active work before implementation. Keep IDs stable; child slices do not complete their parent.
- While editing a contract/docs file, put `<!-- LIVE EDIT: agent/branch editing for ID, started date time. Do not edit this file until this marker is removed. -->` first. Respect another editor's marker; remove yours at completion/handoff.
- The tracker is the only checklist. Check features only after all criteria pass, with date and evidence in the same change. Reopen invalid claims. Keep incomplete features open with exact remaining work.
- Use [the evidence template](docs/evidence/README.md). Separate pure tests, native fixtures and live playthroughs. Grants/repositioning/compiled JARs do not prove earned progress.
- Update affected user docs and manifest. Never invent passed release gates. Finish with feature IDs, validation and next dependency. Keep handoffs concise; no automatic monitor is required.

## Boundaries
- Java 21 and manifest-pinned Minecraft/Fabric/dependencies. No silent upgrades.
- Separate player identity, administrative access, team membership and body. Legacy `Companion`, `ownerId`, `OperatingMode`, module/SQL/NBT names preserve compatibility, not product meaning. Do not casually rename saved keys or delete bodies.
- New orchestration belongs in `PlayerRuntime`; local decisions use `PlayerDecisionLoop`, `TaskDirector` and `TaskPreferences`. Core sees immutable observations, never Minecraft objects. World access stays on the adapter's server thread; IO never blocks ticks.
- Reuse one `ActionArbiter`, `SkillRunner`, checkpoint mechanism and cancellation barrier. Survival, combat, follow and work cannot own independent body controllers. Stop revokes synchronously and invalidates late callbacks.
- F-25b qualifies native server-player mechanics. The mob body is a compatibility backend, not a foundation to extend indefinitely. Prefer native player inventory, hunger, mining/tool use, crafting, combat, death/respawn and portals.
- Physical items remain in native saves; metadata uses the existing ordered SQLite writer. Recheck policy, revisions, activity and claims at every mutation. Ambiguous outcomes block for reconciliation; never replay blindly or recreate items.
- Autonomy is normal, subject to server policy and installed capabilities. Human presence and a mode toggle cannot gate new decisions. Preserve legacy restrictions until explicit tested migration. Server activity limits and inference budgets are separate.
- Local code handles routine survival, navigation, recipes, task choice and recovery. Optional Claude/OpenAI APIs belong in `companion-model`; no Jev or mandatory hosted orchestration. No per-tick inference or generated executable code.
- Team assignments and reserved stock drive cooperation; speech describes verified knowledge/commitments. Personality uses existing bounded weights, not jobs or permissions. Reuse `SocialBrain` and listener limits.
- Earn all progress: no free gear, copied usable items, teleport shortcuts, hidden-resource omniscience or invented achievements. Dragon completion is a production objective; execute only qualified encounters under server policy.
- Preserve audience consent/privacy, grounded correctable memory and peer-specific relationships. Rapport never grants control or justifies revenge. Rich social features enrich capable players, not replace survival engineering.
- Unqualified autonomy/survival/travel remains disabled. Policy tests do not authorize native gameplay.

## Validation
Use JDK 21 and the wrapper; start with affected modules:
```powershell
.\gradlew.bat build
.\gradlew.bat :companion-testkit:run
.\gradlew.bat :companion-testkit:runPersonalityDemo
.\gradlew.bat :companion-server-adapter:runGametest
```
Native tests complement ordinary-client, restart/death/conservation, zero-human and multi-seed tests. For docs-only changes verify links/IDs/consistency without claiming runtime tests.
